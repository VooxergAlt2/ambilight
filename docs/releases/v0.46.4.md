# Ambilight ESP32-C6 v0.46.4

v0.46.4 removes the old fixed 230-LED-per-output / 920-LED-total firmware
policy limits and changes RGB/DDP/PARLIO/per-pixel-gain storage to follow the
active runtime topology.

Existing v0.46.3 settings are preserved. The persisted LED topology schema did
not change.

## Highlights

- **No separate fixed aggregate LED-count ceiling** such as the old 920 limit; the four `uint16_t` side fields represent up to 262,140 LEDs total by format.
- Each of the four side lengths remains stored as `uint16_t`, so the persisted
  format represents `1..65535` LEDs per side.
- Aggregate logical offsets/counts use wider runtime types and are tested above
  65,535 total LEDs.
- Main RGB frames, DDP staging/coverage, PARLIO lane buffers, and ToF/render
  per-pixel gain fields now size themselves from the active topology.
- PARLIO uses the longest configured side as the physical lane length, so the
  normal 230/160 reference installation does not pay the wire-time cost of an
  arbitrary large maximum.
- Topology changes preflight RGB memory and then update PARLIO/DDP/renderer/ToF
  transactionally. Allocation failure rejects/rolls back the requested topology
  instead of partially applying it.
- Optional ToF gain-field allocation is fail-open: normal DDP Ambilight remains
  available even if the correction field cannot be allocated.
- Web UI, JSON backup validation, serial parsing and commissioning no longer
  enforce the historical 230/920 policy limits.

## Hardware validation scope

**Physical hardware has been tested up to 230 LEDs on a single output.**

Configurations above 230 LEDs on one output are accepted by the software path,
but have not yet been validated with a real longer strip. Their practical limit
is determined by ESP32-C6 free heap, PARLIO/LiteLED allocation, power/wiring,
and LED wire time / required frame rate.

The host test suite deliberately exercises cases beyond the old bounds:

- aggregate topology: **120,000 logical LEDs** with logical start > 65,535;
- dynamic gain field: **80,000 entries**, including indices 60,000 and 79,999;
- DDP assembler runtime frame sizing above the old 920-LED capacity.

These are software/addressing tests, not claims that those extreme counts are
practical on one ESP32-C6 installation.

## Settings / upgrade compatibility

`LedMappingProfile` remains schema **3** and its persisted layout is unchanged:
four `uint16` side lengths plus lane/direction fields. v0.46.3 topology, Wi-Fi,
brightness, mask, ToF and other NVS settings therefore require no migration and
are not reset by this update.

For a normal update, use `firmware.bin` at `0x10000`. Do not erase flash first.
The combined `firmware.factory.bin` remains a blank-device/first-install image
and may overwrite NVS.

## Which binary should I use?

| File | Purpose | Flash offset | Settings |
| --- | --- | ---: | --- |
| `firmware.factory.bin` | First install / blank board. Combined bootloader + partition table + boot app + firmware. | `0x0` | May overwrite NVS; do not use as a normal update image. |
| `firmware.bin` | Normal update of an already configured controller. | `0x10000` | Preserves the dedicated NVS partition. |
| `bootloader.bin` | Advanced recovery/component flashing only. | `0x0` | Not needed for normal updates. |
| `partitions.bin` | Current 16 MiB partition table. Advanced recovery only. | `0x8000` | Changing partition tables is an advanced operation. |
| `boot_app0.bin` | OTA boot selector helper used by the factory image. | `0xE000` | Not needed for normal updates. |
| `SHA256SUMS.txt` | SHA-256 hashes of release binaries. | - | Verify downloaded files. |

## Windows quick install

Install Python and esptool:

```powershell
py -m pip install --upgrade esptool
```

First installation on a blank controller:

```powershell
py -m esptool --chip esp32c6 --port COM5 write-flash 0x0 firmware.factory.bin
```

Normal update while preserving settings:

```powershell
py -m esptool --chip esp32c6 --port COM5 write-flash 0x10000 firmware.bin
```

Replace `COM5` with the actual board port. Do **not** run `erase-flash` before a
normal update. A JSON configuration backup from **System -> Configuration
backup** is recommended before maintenance.

## HyperHDR

No custom Windows plugin is required. Configure the controller as a standard
DDP network LED device:

- protocol: DDP;
- port: UDP/4048;
- address: controller IP;
- LED count: the sum of the four active sides shown in the Web UI.

Do not select WLED realtime UDP or HyperHDR Hyperk for this firmware.

- 16 MiB partition check: **PASS**, application slot **7,340,032 bytes**;
- embedded Web UI structural/localization check: **PASS**;
- native tests: **272 / 272 PASS**;

## Known limitations

- Uploading firmware over Wi-Fi / OTA is not implemented yet. The flash layout
  already reserves two application slots for future OTA work.
- The Web UI has no separate authentication; keep HTTP/80 on a trusted LAN.
- Wi-Fi passwords are intentionally excluded from JSON backups.
- Counts above 230 LEDs on one physical output have not yet been hardware-tested.

# Ambilight ESP32-C6 v0.46.4 — описание на русском

В v0.46.4 удалены старые искусственные ограничения **230 LED на выход** и
**920 LED суммарно**. RGB/DDP/PARLIO и per-pixel gain буферы теперь формируются
по фактической активной топологии.

Настройки от v0.46.3 сохраняются: формат и версия NVS-профиля топологии не
изменились.

## Основные изменения

- В runtime больше нет отдельного фиксированного общего лимита вроде 920; четыре `uint16_t` стороны представляют до 262 140 LED суммарно по формату.
- Длина каждой из четырёх сторон по-прежнему хранится как `uint16_t`, то есть
  формат настройки представляет `1..65535` LED на сторону.
- Суммарные логические индексы и размеры кадров используют более широкий тип и
  не переполняются после 65 535 LED.
- RGB-кадры, DDP staging/coverage, PARLIO-буферы и ToF/render gain field теперь
  масштабируются по активной топологии.
- PARLIO выделяет длину линии по самой длинной текущей стороне, поэтому обычная
  конфигурация 230/160 не передаёт огромный пустой хвост каждый кадр.
- Смена топологии сначала проверяет возможность выделить память, затем
  транзакционно перестраивает PARLIO/DDP/renderer/ToF. При ошибке новая
  конфигурация отклоняется или откатывается.
- Если не хватает памяти именно на необязательную ToF-коррекцию, она переходит
  в fail-open, а обычный Ambilight по DDP продолжает работать.
- Web UI, backup validator, serial parser и commissioning больше не содержат
  старых ограничений 230/920.

## Что реально проверено на железе

**На физическом устройстве проверено до 230 LED на одном выходе.**

Значения больше 230 программно разрешены, но с более длинной реальной лентой
пока не проверялись. Практический предел будет зависеть от свободной памяти
ESP32-C6, выделения PARLIO/LiteLED, питания/проводки и допустимого времени
передачи кадра по LED-линии.

В host-тестах отдельно проверяются большие адресные пространства:

- топология **120 000 логических LED**, включая logical start выше 65 535;
- gain field **80 000 элементов**, включая индексы 60 000 и 79 999;
- DDP frame больше старого предела 920 LED.

Это тесты корректности программной адресации, а не обещание практической работы
120 тысяч физических LED на одной ESP32-C6.

## Совместимость настроек

`LedMappingProfile` остаётся schema **3**. В NVS всё так же хранятся четыре
`uint16` длины сторон плюс lane/direction, поэтому существующие настройки
v0.46.3 не требуют миграции и не сбрасываются.

Для обычного обновления используйте `firmware.bin` по адресу `0x10000` без
`erase-flash`. `firmware.factory.bin` предназначен для первой установки на
чистую плату и может перезаписать NVS.

## Какой BIN использовать

| Файл | Назначение | Offset | Настройки |
| --- | --- | ---: | --- |
| `firmware.factory.bin` | Первая установка / пустая плата, полный combined image. | `0x0` | Может перезаписать NVS. |
| `firmware.bin` | Обычное обновление уже настроенного контроллера. | `0x10000` | Сохраняет отдельный NVS-раздел. |
| `bootloader.bin` | Ручное восстановление / advanced flashing. | `0x0` | Для обычного обновления не нужен. |
| `partitions.bin` | Таблица разделов 16 MiB. | `0x8000` | Advanced recovery. |
| `boot_app0.bin` | Служебный OTA boot helper. | `0xE000` | Для обычного обновления не нужен. |
| `SHA256SUMS.txt` | SHA-256 бинарников релиза. | - | Для проверки файлов. |

## Быстрая установка в Windows

```powershell
py -m pip install --upgrade esptool
```

Первая установка:

```powershell
py -m esptool --chip esp32c6 --port COM5 write-flash 0x0 firmware.factory.bin
```

Обновление с сохранением настроек:

```powershell
py -m esptool --chip esp32c6 --port COM5 write-flash 0x10000 firmware.bin
```

Замените `COM5` на порт платы. Перед обычным обновлением не выполняйте
`erase-flash`. Перед обслуживанием рекомендуется скачать JSON backup из
**System -> Configuration backup**.

## HyperHDR

Отдельный Windows-плагин не требуется. Контроллер настраивается как обычное
DDP-устройство:

- протокол: DDP;
- порт: UDP/4048;
- адрес: IP контроллера;
- LED count: сумма четырёх активных сторон из Web UI.

WLED realtime UDP и HyperHDR Hyperk для этой прошивки использовать не нужно.
